= Contributing to AffineScript Libraries
:toc:

This document outlines how to contribute to the AffineScript Libraries project.

== Code of Conduct

By participating in this project, you agree to abide by our
link:CODE_OF_CONDUCT.adoc[Code of Conduct].

== Getting Started

=== Prerequisites

1. **AffineScript Compiler** — Required to build libraries
   - Repository: https://github.com/hyperpolymath/affinescript
   - Status: Early development (parser 0% complete as of 2026-10-05)

2. **Build System** — `just` is used for build orchestration
   - Installation: See https://just.systems/man/en/installation.html
   - Version: 1.0+

3. **Version Control** — Git for source management

=== Setting Up

[source,bash]
----
# Clone the repository
git clone https://github.com/metadatastician/affinescript-libraries.git
cd affinescript-libraries

# Show available commands
just
----

== Development Workflow

=== Branch Strategy

* **main** — Stable releases (protected)
* **develop** — Integration branch for next release
* **feature/*** — Feature branches (prefix with feature/)
* **fix/*** — Bug fix branches (prefix with fix/)
* **docs/*** — Documentation branches (prefix with docs/)

=== Commit Messages

Follow the https://www.conventionalcommits.org/[Conventional Commits] specification:

* `feat:` — New features
* `fix:` — Bug fixes
* `docs:` — Documentation changes
* `style:` — Code style changes (formatting, etc.)
* `refactor:` — Code refactoring
* `perf:` — Performance improvements
* `test:` — Adding or modifying tests
* `chore:` — Build process or auxiliary tool changes
* `revert:` — Revert a previous commit

=== Pull Requests

1. Fork the repository
2. Create a feature/fix/docs branch
3. Make your changes
4. Run tests: `just test`
5. Run validation: `just validate`
6. Open a PR to the develop branch

== Library Conventions

=== Module Structure

Each library module should:

1. Have a clear module docstring
2. Export types and functions via module interface
3. Include inline documentation for public API
4. Follow AffineScript naming conventions

[source,affine]
----
// SPDX-License-Identifier: MPL-2.0
// SPDX-FileCopyrightText: 2026 ...

/**
 * Module documentation explaining purpose and usage.
 * 
 * @example Basic usage example
 */
module MyLibrary

// Type definitions
type MyType = { ... }

// Public functions
/**
 * Function documentation.
 * 
 * @param x - Description of parameter
 * @returns Description of return value
 */
myFunction :: MyType -> string
myFunction x = ...
----

=== Error Handling

Use Result types for fallible operations:

[source,affine]
----
/**
 * A result that can succeed or fail.
 */
type Result<T, E>
  = Ok of T
  | Err of E

parseYaml :: string -> Result<KYamlFile, ParseError>
parseYaml input = ...
----

=== Testing

Tests should be placed in `tests/` directory with the same structure as `src/`.

[source,affine]
----
module Test.Kyaml

import Kyaml

testParseValidYaml :: IO<()>
testParseValidYaml = do
  let yaml = "apiVersion: v1\nkind: Pod\nmetadata:\n  name: test"
  let result = Kyaml.parse yaml
  case result of
    ParseSuccess _ -> putStrLn "✓ Valid YAML parsed"
    ParseFailure errors -> putStrLn ("✗ Parse failed: " ++ show errors)
----

== Style Guide

=== Naming Conventions

* **Modules**: PascalCase (e.g., `Kyaml`, `Kyaml.Query`)
* **Types**: PascalCase (e.g., `KYamlFile`, `ParseResult`)
* **Functions**: camelCase (e.g., `parseYaml`, `queryResource`)
* **Variables**: camelCase (e.g., `inputString`, `resultValue`)
* **Constants**: SCREAMING_SNAKE_CASE (e.g., `MAX_LENGTH`, `DEFAULT_TIMEOUT`)

=== Formatting

* Indentation: 2 spaces (no tabs)
* Line length: 100 characters maximum
* Opening braces on same line for short definitions
* Opening braces on new line for multi-line definitions
